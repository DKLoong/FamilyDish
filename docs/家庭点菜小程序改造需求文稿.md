# FamilyDish · 家庭点菜小程序改造需求文稿

## 一、项目背景

基于开源项目 **PairBite**（微信小程序 + 微信云开发）进行改造。PairBite 原本是“情侣点菜”工具：两人绑定后，一方点菜，另一方接单。现将其定位从“情侣”改为“家庭”，服务于一个家庭组内的多名成员。

改造后，小程序同时具备以下能力：

- 家庭成员共享菜品库。
- 查看食材清单和烹饪步骤。
- 显式提交点菜，并共享点菜记录。
- 根据点菜时尚未准备的食材生成家庭购物清单。
- 随机选菜和搜索（菜名与食材）。
- 在记录页通过微信原生分享，把小程序卡片发给家庭成员。

参考产品：微信小程序“一键食谱”。只参考其菜谱详情页的交互设计，不复制其菜谱文字、图片或其他内容。

## 二、产品定位与范围

### 2.1 产品定位

一个私人、家庭用的极简点菜、菜谱和购物清单工具。家庭成员可以共同维护菜品，决定吃什么，查看做法，并协同准备需要购买的食材。

### 2.2 首版必须包含

1. 家庭创建、邀请、加入、退出、解散和成员管理。
2. 创建者、管理员、普通成员三级角色权限。
3. 家庭内昵称和家庭成员人数上限。
4. 家庭共享菜品库及菜品分类。
5. 菜谱详情、食材“已准备”勾选和步骤计时器。
6. 显式点菜、点菜记录和状态流转。
7. 点菜时保存完整菜品快照。
8. 家庭共享购物清单。
9. 随机选菜和搜索（菜名与食材）。
10. 记录页微信原生分享告知。
11. 5 道自行整理的示例菜。
12. 完整的加载、空状态、失败提示和验收测试。

### 2.3 二期计划

- 多家庭切换。
- 使用云数据库 `watch` 实现实时监听。
- 营养计算。
- 评论和点赞。
- 第三方菜谱导入适配器。

### 2.4 首版明确不做

- 多人同时编辑同一菜品时的协作冲突处理。
- 指定厨师和复杂接单流程。
- 按份数缩放食材用量。
- 购物清单的部分购买。例如，只购买合并数量中的一部分。
- 离线点菜和离线购物清单同步。
- 第三方菜谱抓取、批量导入和公共导入接口。
- 后台计时通知。
- 订阅消息、服务端推送通知及其授权与额度管理。
- 生成菜单长截屏后分享图片。

## 三、家庭组管理

### 3.1 入口与归属

- 用户首次进入时，展示“创建家庭”和“加入家庭”两个入口，不自动创建家庭。
- 首版中，一个用户最多属于一个有效家庭。
- 已加入家庭的用户点击其他邀请时，提示“你已加入家庭 X”。不自动退出，也不自动切换家庭。
- 已退出、被移除或所在家庭已解散后，用户可以重新创建或加入家庭。
- 数据结构上预留多家庭扩展能力。
- 创建家庭时必须填写家庭名称，长度为 1–12 个字。
- 创建者和管理员可以修改家庭名称，普通成员不可修改。
- 家庭名称用于首页、邀请卡片和「我的」页展示。

### 3.2 家庭内昵称

- 创建或加入家庭时，用户必须填写“家庭内昵称”。
- 昵称长度为 1–20 个字符。
- 成员可以修改自己的家庭内昵称。
- 点菜记录保存点菜人昵称快照。后续改名不影响历史记录。
- 首版不依赖微信头像和昵称授权，不向成员展示 `openid`。

### 3.3 角色与权限

| 操作 | 普通成员 | 管理员 | 创建者 |
| --- | --- | --- | --- |
| 查看菜品、菜谱和家庭点菜记录 | 可以 | 可以 | 可以 |
| 点菜、随机选菜、搜索 | 可以 | 可以 | 可以 |
| 取消或完成自己的待做记录 | 可以 | 可以 | 可以 |
| 取消或完成家庭内任意待做记录 | 不可以 | 可以 | 可以 |
| 添加购物项目、勾选已购买 | 可以 | 可以 | 可以 |
| 删除自己添加的购物项目 | 可以 | 可以 | 可以 |
| 删除任意购物项目、清空已购买项目 | 不可以 | 可以 | 可以 |
| 管理菜品和分类 | 不可以 | 可以 | 可以 |
| 生成或重新生成邀请码 | 不可以 | 可以 | 可以 |
| 修改家庭人数上限 | 不可以 | 可以 | 可以 |
| 修改家庭名称 | 不可以 | 可以 | 可以 |
| 移除普通成员 | 不可以 | 可以 | 可以 |
| 移除管理员 | 不可以 | 不可以 | 可以 |
| 授予或撤销管理员权限 | 不可以 | 不可以 | 可以 |
| 解散家庭 | 不可以 | 不可以 | 可以 |

补充规则：

- 创建者是固定超级管理员，其身份不可被撤销。
- 被邀请人加入后默认为普通成员。邀请他人不会自动获得管理员身份。
- 创建者不能移除自己。
- 已完成、已取消的点菜记录不可再次变更，也不能删除。
- 管理员和创建者不能删除已经发生的历史点菜记录。

### 3.4 邀请与加入

- 创建者或管理员可以生成邀请码或分享卡片。
- 邀请信息只携带邀请码，不携带 `familyId`。加入时由服务端按邀请码反查家庭，减少内部 ID 暴露。
- 邀请码由服务端生成，为 6 位字母数字，字符集为 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（32 字符，去除易混淆字符）。
- 邀请码不区分大小写，加入时统一转大写后校验。
- 不使用纯数字邀请码，降低被穷举风险。
- 邀请码默认三天有效，有效期内可供多人使用。
- 重新生成邀请码后，旧码立即失效。
- 云函数必须限制频繁错误尝试，降低邀请码被穷举的风险。
- 加入家庭前，云函数必须校验：
  - 用户当前是否已属于有效家庭。
  - 目标家庭是否有效。
  - 邀请码是否正确且未过期。
  - 家庭是否还有剩余名额。
- 成员资格、邀请码有效性和剩余名额校验必须一次性完成。涉及多条数据时使用事务，避免并发加入导致人数超限。

### 3.5 家庭人数上限

- 默认上限为 10 人。
- 创建者和管理员可以在设置中修改。
- 可设置范围为“当前有效成员数至 50 人”。
- 修改上限不影响现有成员。
- 达到上限后，新成员无法加入，并提示联系家庭管理员。

### 3.6 退出、移除与解散

- 普通成员和管理员可以主动退出家庭。
- 创建者不能直接退出，只能解散家庭。
- 解散家庭需要二次确认。
- 首版解散只将家庭标记为“已解散”，并阻断所有成员继续访问，不立即物理删除数据。
- 退出、被移除或家庭解散后，用户失去后续访问权限。
- 历史点菜记录和菜品快照继续保留。

## 四、点菜与菜谱详情

### 4.1 查看与点菜分离

- 用户进入菜谱详情页时，不生成点菜记录。
- 用户点击“我要点这道菜”并完成确认后，才生成点菜记录。
- 一条点菜记录代表“一道菜在一个餐次内要做一次”，不是“一次点击动作”。
- 记录去重键为：家庭 + 菜品 + 用餐日期 + 餐次 + 待做状态。
- 去重键已有待做记录时，不新建记录，只把当前用户加入该记录的点菜人列表。
- 多人点同一道菜不增加采购量。采购量首版只取决于菜谱用量，与点菜人数无关。
- 同一用户重复点同一道菜时，不重复追加点菜人，返回“你已点过这道菜”。
- 已完成或已取消的记录不参与合并。再次点同一道菜时新建记录，用于“中午吃了，晚上还想吃”的场景。
- 首版不填写份数，不做食材用量按份数缩放。

### 4.2 点菜确认信息

点菜确认页提供以下选填项，任何一项未填都不阻断提交：

- 用餐日期：默认显示“今天”，可修改或清除；清除后不写入字段。
- 餐次：早餐、午餐、晚餐、其他。默认不选中；未选择时不写入字段。
- 备注：上限 100 字。

以下信息由系统自动记录：

- 点菜时间。
- 点菜人列表及各自的家庭内昵称快照。
- 完整菜品快照。
- 初始状态“待做”。

合并到已有记录时：

- 保留首次点菜的用餐日期、餐次和备注，后续点菜人的备注不写入。
- 后续点菜人认为“未准备”的食材，若该记录下还没有对应购物项，需要补建。

### 4.3 状态流转

点菜记录只有以下三种状态：

- 待做。
- 已完成。
- 已取消。

权限和约束：

- 普通成员可以取消或完成自己点过的待做记录。
- 管理员和创建者可以取消或完成家庭内任意待做记录。
- 多人合并的记录，任一参与点菜的人都可以完成或取消整条记录。
- 取消是整条取消，不拆分为“退出自己那一份”。
- 完成和取消都需要二次确认。
- 已完成、已取消的记录不可再次变更，也不能删除。
- 状态变更必须由云函数校验当前状态和操作权限。
- 点菜使用唯一请求标识，防止重复提交生成多条记录。

取消点菜的二次确认文案必须说明：

> 取消后将同时移除本次点菜带入的购物清单项目。

多人点过的记录还要说明参与人数：

> 这道菜有 2 人点过，取消后一并移除。

### 4.4 菜谱详情页

在 PairBite 原有 `DishDetail` 页面基础上扩展：

- 菜品名称、图片、分类和描述。
- 食材清单。
- 有序烹饪步骤。
- 难度、总耗时和小贴士。
- 每步建议时长和计时入口。

### 4.5 食材“已准备”勾选

- 菜谱中的每项食材都有“已准备”勾选框。
- 勾选状态按用户和菜品保存在本地，不同步到云端。
- 提供“一键清除”功能。
- 菜谱内容修改后，重置该菜品的旧勾选状态，避免与新食材不匹配。
- 勾选状态只在点菜时影响购物清单生成。
- 点菜完成后，再修改本地勾选状态，不修改已经生成的购物清单。

### 4.6 步骤计时器

- 开始计时时保存结束时间戳。
- `setInterval` 只负责刷新页面上的剩余时间。
- 页面重新显示时，根据结束时间戳重新计算。
- 每个详情页首版只允许一个进行中的计时器。
- 启动其他步骤的计时器前，需要确认是否切换。
- 不做后台通知。
- 计时结束时若页面不可见，用户返回后显示“已到时”。

## 五、家庭共享购物清单

### 5.1 基本原则

每个家庭只有一份共享购物清单。

购物清单采用以下模型：

> 底层按来源分别存放，页面按规则合并显示。

不得在数据库中只保存一条无法拆分的合并项目。每项食材必须保留来源，以便取消点菜时只移除对应来源，不影响其他点菜或手工项目。

### 5.2 购物来源记录

每条购物来源记录至少包含：

- `familyId`。
- 来源类型：点菜或手工。
- `orderId`。手工项目为空。
- `dishId`。手工项目可以为空。
- 食材名称、数量、单位和备注快照。
- 已购买状态、购买人和购买时间。
- 创建人和创建时间。

### 5.3 点菜生成购物项目

- 点菜时，系统读取菜谱中未标记“已准备”的食材。
- 用户确认点菜后，只为这些未准备食材创建购物来源记录，并关联本次 `orderId`。
- 已标记“已准备”的食材不加入购物清单。
- 点菜记录和购物来源记录必须保证一致性，避免点菜成功但清单生成不完整。
- 若所有食材均已准备，则只创建点菜记录，不创建购物来源记录。
- 不额外弹出重复的食材选择窗口。

### 5.4 手工添加

- 用户可以在购物清单页面手工添加项目。
- 名称必填。
- 数量、单位和备注选填。
- 手工项目没有 `orderId`。

### 5.5 合并显示规则

未购买项目按「食材名称 + 单位」分组，再按有无数值分成两类：

- 名称相同、单位相同、且都有数值数量的项目合并显示，数量为各项数值之和。
- 名称相同、单位相同、且都没有数值数量的项目合并显示为一行，备注去重后并列展示，例如“适量”或“适量、少许”。
- 名称相同、单位相同，但一部分有数值、一部分没有数值的，分为两行显示。

其他情况独立显示，包括：

- 名称相同但单位不同的项目。
- 已购买项目与未购买项目。

已购买项目不参与新项目的合并。之后新增相同食材时，生成新的未购买显示组，不改变原来的已购买组。

### 5.6 已购买

- 所有家庭成员都可以勾选“已购买”。
- 勾选合并项目时，将当前合并组内的所有来源记录一起标记为已购买。
- 首版不支持部分购买。
- 取消勾选时，按同一组来源记录恢复为未购买。

### 5.7 删除与点菜取消

- 普通成员可以删除自己添加的购物项目。
- 管理员和创建者可以删除任意购物项目，并清空已购买项目。
- 取消点菜时，只删除该 `orderId` 关联的购物来源记录。
- 删除后，购物清单根据剩余来源记录重新合并计算。
- 完成点菜记录不自动修改购物清单。
- 修改本地“已准备”状态不自动修改购物清单。
- 删除购物项目不影响点菜历史或菜品快照。

## 六、菜品库与菜谱内容

### 6.1 共享与维护

- 家庭组内所有成员共享同一个菜品库。
- 所有成员可以查看菜品。
- 创建者和管理员可以新增、修改和归档菜品，并管理分类。
- 普通成员不能修改菜品库。

### 6.2 菜品字段

保留 PairBite 原有字段，并扩展以下内容：

- 名称。
- 图片。
- 分类。
- 描述。
- 食材清单。
- 烹饪步骤。
- 难度。
- 总耗时。
- 小贴士。
- 归档状态。

必填规则：

- 菜品名称必填。
- 至少一项食材。
- 至少一个烹饪步骤。

图片、难度、总耗时和小贴士选填。

### 6.3 食材结构

食材必须使用结构化数组，不使用自由文本：

```text
{
  name: "排骨",
  quantity: 500,
  unit: "g",
  note: ""
}
```

无具体数量时：

```text
{
  name: "盐",
  quantity: null,
  unit: "",
  note: "适量"
}
```

规则：

- `quantity` 为数值或 `null`。
- `unit` 和 `note` 可以为空。
- 页面展示时将数量、单位和备注组合为易读文本。
- 搜索匹配菜名与食材 `name`，不匹配用量和备注。

### 6.4 烹饪步骤

步骤使用有序数组。每步包含：

- 步骤描述。
- 建议时长，可选。
- 步骤图片，可选。

### 6.5 菜品快照与归档

- 点菜时保存菜品名称、图片、食材、步骤、难度、总耗时和小贴士快照。
- 历史点菜记录始终读取快照，不受后续菜品修改或归档影响。
- 菜品“删除”在首版统一改为“归档”。
- 归档菜品不再出现在选菜、随机选菜和搜索结果中。
- 归档不物理删除菜品记录，也不影响历史点菜记录。

### 6.6 示例菜

- 首版准备 5 道自行整理的示例菜。
- 可以检索公开菜谱作为事实参考，但必须重新整理食材、用量和步骤文字。
- 不复制第三方图片，不做批量抓取。
- 在内部保留参考来源记录。
- 示例菜全部具有完整食材和步骤，并至少覆盖：
  - 可合并的数值用量。
  - 无具体数量的“适量”。
  - 无步骤图片。
  - 多个菜品分类。
  - 不同总耗时。

### 6.7 后续导入扩展点

- 首版只定义统一的菜谱输入结构和校验函数。
- 手动录入与未来导入都复用这套结构和校验。
- 第三方适配器放到二期。
- 首版不开放公共导入接口，也不预置抓取代码。

### 6.8 分类管理

- 分类由名称和排序组成，同一家庭内不允许重名。
- 创建者和管理员可以新增分类、重命名分类、调整分类顺序、删除分类。
- 分类名称长度为 1–12 个字。
- 分类表是分类的唯一来源。首页筛选、菜谱表单的分类候选、分类管理页三处必须读取同一份数据，不允许各自维护。
- 重命名分类时，使用该分类的菜品必须同步更新为新的分类名称。同步只改分类字段，不改变菜品内容版本，因此不会重置食材「已准备」勾选。
- 删除分类时，若仍有菜品使用该分类，必须二次确认；确认后删除分类，并把这些菜品的分类清空为未分类。
- 删除分类时必须同时清空菜品上的分类文本，否则下次同步会把已删除的分类补回来。
- 在菜谱表单里输入分类表中没有的名称时，保存菜品前自动登记该分类，使首页和分类管理页立即同步。
- 首次进入分类管理页或菜谱表单时，若分类表为空，系统把菜品中已存在但未登记的分类自动补入，避免出现空列表。
- 首页分类筛选的顺序以分类表为准；仅在分类表为空时退回菜品出现顺序，作为兜底。

## 七、随机选菜与搜索

### 7.1 随机选菜

- 在首页或菜品列表页提供“随机一下”入口。
- 只从当前家庭未归档菜品中随机抽取。
- 抽取后进入菜谱详情页，不自动生成点菜记录。
- 没有可用菜品时显示空状态，不执行跳转。

### 7.2 搜索

- 用户可以输入菜名或食材名，例如“红烧”或“鸡”。
- 同时匹配菜品 `name` 与 `ingredients` 数组中的 `name`，均为包含匹配。
- 菜名命中的结果排在仅食材命中的结果之前。
- 初版使用简单 `includes`，不做分词和同义词。
- 搜索结果复用菜品卡片组件。
- 点击结果进入菜谱详情页，不自动生成点菜记录。
- 菜品量较小时，可以拉取当前家庭菜品后在前端内存过滤。
- 菜品量增大后，再考虑云端过滤和索引优化。

## 八、分享告知

### 8.1 定位

- 首版不做订阅消息、服务端推送和任何形式的自动通知。
- 点菜成功后，用户可在记录页主动把小程序分享给好友或家庭群，省去对方查找小程序的步骤。
- 分享走微信原生转发能力。不自建消息通道，不生成图片，不生成小程序码，不生成菜单长截屏。

### 8.2 实现规则

- 记录页设置一个常驻圆形「分享」图标按钮，居中显示在页面底部、底部导航栏上方。
- 点击按钮触发微信「发送给」好友／群选择页。页面必须定义 `onShareAppMessage`，否则转发入口不可用。
- `onShareAppMessage` 同步返回标题与 `path`。标题包含家庭名称，`path` 固定指向点菜记录页，不带任何查询参数。
- 不传 `imageUrl`，由微信使用当前页面默认截图作为卡片图。
- 分享卡片不携带 `familyId` 或其他业务参数。成员点开后，云函数按 `openid` 与 `UserFamily` 判定家庭归属，展示本人所在家庭的数据。
- 非本家庭成员点开后正常进入其自己的家庭，不做特殊分支。尚未加入任何家庭的新用户，沿用基线全局绑定守卫进入创建／加入流程。
- 点菜成功后显示轻提示「已点菜，可分享给家人」。不分享、取消分享或分享失败，均不影响点菜结果。
- 分享为纯前端能力。不调用云函数，不写入数据库，不产生新的异常状态。

### 8.3 按钮规格

- 56px 圆形，主色实心，白色 24px 分享图标，线宽 1.5px。
- 下边距为底部导航高度加 16px。列表底部留白须避开按钮。
- 使用 `button` 组件并清除默认样式，配 `aria-label` 供读屏使用。视觉上不显示文字。
- 详细尺寸与状态见《design-spec.html》。

### 8.4 验收标准

- 按钮常驻且不被列表遮挡；点击能拉起微信转发选择页。
- 卡片标题、`path` 与默认截图符合本节约定。
- 本家庭成员点开后看到本家庭记录；非本家庭成员点开后看到其本人家庭记录，无越权。
- 真机验证。不以开发者工具调用成功作为依据。

## 九、数据模型与安全约束

### 9.1 数据模型迁移

- 将 `DishList`、`OrderList`、`Category` 等集合中的 `coupleId` 替换为 `familyId`。
- 新增购物来源记录集合，保存家庭购物项目及其 `orderId` 来源。
- 不保留旧线上数据兼容逻辑。
- 旧测试集合手动清理，不编写历史数据迁移脚本。

### 9.2 Family

`Family` 至少包含：

- 家庭名称：创建时必填，1–12 个字；创建者、管理员可改名。
- `createdBy`，固定为创建者 `openid`。
- `memberOpenids`，只作冗余展示使用。
- 家庭人数上限。
- 家庭状态。
- 当前邀请码及有效期，或使用独立的邀请数据。
- 创建时间和更新时间。

### 9.3 UserFamily

新增 `UserFamily` 集合，作为权威成员关系，至少包含：

- `openid`。
- `familyId`。
- `role`：`owner`、`admin`、`member`。
- 家庭内昵称。
- `joinedAt`。

首版每个 `openid` 最多有一条有效记录。`Family.memberOpenids` 只作冗余展示，不能作为鉴权依据。

### 9.4 OrderList

点菜记录至少包含：

- `orderId` 和 `familyId`。
- `dishId` 和完整菜品快照。
- 点菜人列表 `orderers`，每项含 `openid`、家庭内昵称快照和点菜时间，按点菜先后排列。
- 首位点菜人的 `openid` 和昵称单独保留，兼容改造前的记录和既有权限判断。
- 用餐日期、餐次和备注。
- 状态及对应时间。
- 唯一请求标识。
- 购物项条数，供取消时提示。
- 创建时间和更新时间。

一条记录可由多人共同点菜，因此点菜人是数组而不是单值。读取时需要兼容没有 `orderers` 的旧记录，用首位点菜人字段兜底。

### 9.5 读写收口

- 除本地“已准备”状态和本地计时器外，所有共享数据的读取和写入都必须经过云函数。前端不调用 `wx.cloud.database()` 直连数据库。
- 云函数从 `cloud.getWXContext()` 获取 `openid`。
- 云函数查询 `UserFamily`，得到有效 `familyId` 和 `role`。
- 云函数必须校验目标家庭状态、目标数据归属和操作权限。
- 前端直接写入 `OrderList` 的逻辑和各页面 `app.database()` 直连读取必须首先移除。
- 7 个集合（`User`、`Family`、`UserFamily`、`DishList`、`Category`、`OrderList`、`ShoppingItem`）权限统一设为「仅管理端可读写」，不留客户端旁路。

### 9.6 通用入口安全

保留统一云函数入口，但必须增加以下限制：

- 使用“集合 + 操作”白名单。
- 每种操作单独校验允许修改的字段。
- `familyId`、点菜人、角色、创建时间和状态变更由服务端确定。
- 不接受前端指定任意角色、任意家庭或任意受保护字段。
- 加入家庭、点菜、完成和取消等关键操作必须防重复提交。
- 涉及多条数据时使用事务。
- 状态变更使用条件校验，避免两个并发请求同时完成或取消同一记录。

### 9.7 多家庭扩展

- 首版只支持一个有效家庭。
- 将来支持多家庭时，允许同一 `openid` 有多条 `UserFamily` 记录。
- 增加 `activeFamilyId` 和家庭切换入口。
- 所有查询从“取唯一有效家庭”改为“取当前激活家庭”。
- 云函数仍按激活家庭和角色鉴权。

## 十、页面与异常状态

### 10.1 页面改造

- `Bind`：改为创建家庭和加入家庭两个入口，并收集家庭内昵称。
- `MainPage`：移除情侣双人元素。顶部区展示按时间变化的问候语与「家庭名 · 人数」胶囊，其下依次为搜索、分类、随机与菜品列表；顶部区固定，只有列表滚动。首页不展示待做记录，待做与状态流转在记录 tab 查看。
- 菜品管理页：列出在用与已归档菜品，支持新增、编辑、归档与恢复。归档后可从该页恢复，不需要直接改数据库。
- `DishDetail`：增加食材勾选、步骤计时、完整菜谱信息和显式点菜入口。
- `OrderHistory`：按 `familyId` 查询，支持状态流转和记录分享入口。
- 购物清单页：支持合并展示、手工添加、已购买、删除和清空已购买项目。
- 设置页：支持昵称修改、邀请、角色管理、人数上限、退出或解散家庭。

### 10.2 全局拦截

- 修改 `miniprogram/app.js` 中的全局绑定拦截器。
- 判断依据从“是否已绑定伴侣”改为“是否已加入有效家庭”。
- 调整白名单和跳转目标。
- 家庭已解散、成员被移除或成员已退出时，不能继续访问原家庭数据。

### 10.3 加载与失败

所有列表页必须具备：

- 加载中状态。
- 空状态。
- 加载失败状态。
- 重试入口。

所有写操作必须满足：

- 提交期间禁用按钮。
- 明确显示成功或失败结果。
- 防止重复提交。
- 网络失败时由用户主动重试。
- 首版不保存离线写操作队列。
