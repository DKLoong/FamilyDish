## 3. 目标架构

### 3.1 分层

```text
小程序前端（WXML + WXSS + JS）
  ├─ pages/         首页 / 记录 / 购物 / 我的 + 管理与快照页
  ├─ components/    family-guard、dish-card、order-sheet、empty-state
  └─ utils/         api.js、dishSchema.js、shoppingGroup.js、timer.js
            │  wx.cloud.callFunction（读写均经云函数，前端不直连数据库）
            ▼
云函数层（统一入口 + 专用函数）
  ├─ familyApi      白名单 CRUD + 领域动作 + 鉴权 + 事务 + 幂等
  ├─ ensureUser     用户注册与家庭上下文
  └─ getFileURL     云存储临时链接（保留）
            ▼
云数据库 7 个集合 / 云存储（权限统一：仅管理端可读写）
```

前端不调用 `wx.cloud.database()`。列表读取、详情读取与全部写操作都通过 `wx.cloud.callFunction` 走 `familyApi`。7 个集合（`User`、`Family`、`UserFamily`、`DishList`、`Category`、`OrderList`、`ShoppingItem`）的数据库权限统一设为「仅管理端可读写」，不保留任何客户端直连旁路。云存储同样保持「仅管理端可读写」，图片经 `getFileURL` 转临时链接展示。

统一口径的代价是每个列表页多一次云函数调用，收益是权限判断只有一处、无客户端绕过路径。此条为 M0 建集合时的硬性检查项。

### 3.2 云函数职责

| 云函数 | 职责 | 是否保留现有 |
| --- | --- | --- |
| `familyApi` | 全部家庭、菜品、分类、点菜、购物、成员读写。含白名单 CRUD 与领域动作 | 新建，替代 `getCoupleData` / `updateCoupleData` / `manageCategory` / `bindPartner` / `unbindPartner` / `updateKitchenName` |
| `ensureUser` | 首次进入创建 `User` 文档；返回 `UserFamily` 与 `Family` 上下文 | 由 `createUser` 精简改造 |
| `getFileURL` | `cloud://` → 临时链接 | 原样保留 |

`getOpenId` 可并入 `ensureUser`。改造完成后停用旧函数，避免残留可调用入口。

### 3.3 统一入口的两类动作

需求文稿 9.6 要求「集合 + 操作白名单」。本方案采用混合结构：

- **白名单 CRUD**：用于简单集合。客户端传 `collection` 与 `op`，两者都必须在白名单内；每次操作按字段允许表裁剪 `data`。
- **领域动作**：用于跨集合或需要事务的流程，如 `placeOrder`、`cancelOrder`、`joinFamily`。动作名固定，不接收集合名，不接收受保护字段。

所有动作共用一段鉴权中间件：

1. `cloud.getWXContext()` 取 `openid`。
2. 查 `UserFamily` 得有效 `familyId` 与 `role`。
3. 校验 `Family.status === 'active'`。
4. 按动作查权限表。
5. 服务端生成 `familyId`、点菜人、角色、时间戳、状态变更字段。

前端传入的 `familyId`、`role`、`createdBy`、`status`、`createTime` 一律忽略。

## 4. 数据模型

### 4.1 集合总览

| 集合 | 用途 | 隔离键 | 写入方式 |
| --- | --- | --- | --- |
| `User` | 用户身份存根 | `_id = openid` | `ensureUser` |
| `Family` | 家庭主体、状态、人数上限、邀请码 | `_id = familyId` | 领域动作 |
| `UserFamily` | 权威成员关系、角色、家庭内昵称 | `openid + familyId` | 领域动作 |
| `DishList` | 菜品与菜谱 | `familyId` | 白名单 CRUD |
| `Category` | 菜品分类 | `familyId` | 白名单 CRUD |
| `OrderList` | 点菜记录与菜品快照 | `familyId` | 仅领域动作 |
| `ShoppingItem` | 购物来源记录 | `familyId` | 白名单 CRUD + 领域动作 |

`Family.memberOpenids` 仅用于展示，不得作为鉴权依据。

### 4.2 关键字段

**Family**

```text
{
  _id, name,                 // 创建必填 1–12 字；创建者/管理员可改（D2-A）
  createdBy,
  maxMembers: 10,
  status: 'active' | 'dissolved',
  memberOpenids: [],
  invite: { code, expiresAt, generatedBy, generatedAt },  // code: 6 位字母数字，32 字符集，输入转大写（D4-A）
  createTime, updateTime
}
```

**UserFamily**

```text
{
  _id, openid, familyId,
  role: 'owner' | 'admin' | 'member',
  nickname,
  status: 'active' | 'left' | 'removed',
  joinedAt, updateTime
}
```

首版每个 `openid` 最多一条 `status = 'active'` 记录。多家庭扩展时放开此约束并增加 `activeFamilyId`。

**DishList**

```text
{
  _id, familyId, name, image(fileID), category, description,
  ingredients: [{ key, name, quantity: number|null, unit, note }],
  steps: [{ text, minutes, image }],
  difficulty, time, tips,
  archived: boolean,
  version: number,
  createdBy, createTime, updateTime
}
```

`version` 在菜品内容修改时自增。本地「已准备」状态按 `version` 存储，旧勾选自动失效，不需要主动清理。

**OrderList**

```text
{
  _id, orderId, familyId, dishId,
  dishSnapshot: { name, image, ingredients, steps, difficulty, time, tips },
  orderers: [{ openid, nickname, at }],   // 点菜人列表，按点菜先后
  ordererOpenids: [openid],               // 便于判断「是否参与点菜」
  ordererOpenid, ordererNickname,         // 首位点菜人，兼容旧记录与既有权限判断
  mealDate, mealType, remark,
  status: 'pending' | 'completed' | 'cancelled',
  statusTimes: { createdAt, completedAt, cancelledAt },
  shoppingCount,                          // 本单带入的购物项条数，供取消提示
  requestId,
  createTime, updateTime
}
```

去重键为 `familyId + dishId + mealDate + mealType + status(pending)`。需要一条非唯一索引 `idx_family_dish_meal` 覆盖这五个字段。

**ShoppingItem**

```text
{
  _id, familyId,
  sourceType: 'order' | 'manual',
  orderId, dishId,
  ingredient: { name, quantity, unit, note },
  purchased: boolean,
  purchaseGroupId,
  purchasedBy, purchasedAt,
  createdBy, createTime
}
```

### 4.3 索引与约束

| 集合 | 索引 / 约束 |
| --- | --- |
| `UserFamily` | `(openid, status)`；`(familyId, status)`；`active` 记录需保证 `openid` 唯一 |
| `Family` | `invite.code` 唯一；`status` |
| `DishList` | `(familyId, archived)`；`(familyId, createTime)` |
| `Category` | `(familyId, sort)` |
| `OrderList` | `(familyId, createTime)`；`requestId` 唯一 |
| `ShoppingItem` | `(familyId, purchased)`；`(familyId, orderId)`；`(familyId, purchaseGroupId)` |

若云数据库无法对 `UserFamily` 建立条件唯一索引，则在 `joinFamily` 事务内先查后写，并以 `openid` 作为文档 `_id` 的组成部分保证原子性。

## 5. 云函数接口契约

统一响应格式：`{ success, code, message, data }`。`code` 用于前端错误提示与日志检索。

### 5.1 白名单 CRUD

| collection | 允许的 op | 允许角色 | 字段限制 |
| --- | --- | --- | --- |
| `DishList` | `list`、`get` | 全部成员 | 只读；自动附加 `familyId`、`archived = false` |
| `DishList` | `add`、`update`、`archive` | 创建者、管理员 | 名称、图片、分类、描述、食材、步骤、难度、耗时、小贴士、归档状态；`version` 由服务端维护 |
| `Category` | `list` | 全部成员 | 只读 |
| `Category` | `add`、`update`、`remove` | 创建者、管理员 | 名称、排序 |
| `ShoppingItem` | `list` | 全部成员 | 只读；自动附加 `familyId` |
| `ShoppingItem` | `add` | 全部成员 | 仅手工项目：`sourceType = 'manual'`，`orderId = null` |

`inc` 操作删除。首版不需要自增字段。

### 5.2 领域动作

| action | 角色 | 主要入参 | 事务 | 幂等 |
| --- | --- | --- | --- | --- |
| `createFamily` | 任意未加入家庭用户 | `familyName`（必填 1–12 字）、`nickname` | 是 | 按 `openid` 幂等 |
| `regenerateInvite` | 创建者、管理员 | 无 | 是 | 否 |
| `joinFamily` | 任意未加入家庭用户 | `inviteCode`、`nickname` | 是 | 按 `openid` 幂等 |
| `updateCapacity` | 创建者、管理员 | `maxMembers` | 是 | 否 |
| `updateNickname` | 全部成员 | `nickname` | 否 | 否 |
| `renameFamily` | 创建者、管理员 | `name`（必填 1–12 字） | 否 | 否 |
| `listMembers` | 全部成员 | 无 | 否 | — |
| `setRole` | 创建者 | `targetOpenid`、`role` | 是 | 否 |
| `removeMember` | 创建者、管理员（仅普通成员）；创建者（可移除管理员） | `targetOpenid` | 是 | 否 |
| `leaveFamily` | 管理员、普通成员 | 无 | 是 | 否 |
| `dissolveFamily` | 创建者 | 二次确认标识 | 是 | 否 |
| `placeOrder` | 全部成员 | `dishId`、`requestId`、`preparedKeys`；选填 `mealDate`、`mealType`、`remark` | 是 | `requestId` 唯一 |

## 6. 关键流程与事务边界

### 6.1 点菜 `placeOrder`

1. 校验 `requestId` 未使用过。
2. 读取 `DishList` 文档，确认 `archived = false` 且属于当前家庭。
3. 构造 `dishSnapshot`，写入点菜人昵称快照。
4. 从 `ingredients` 中排除 `preparedKeys` 命中的项。
5. 按「`familyId` + `dishId` + `mealDate` + `mealType` + `status = pending`」查询是否已有待做记录：
   - 命中且当前用户已在 `orderers` 中：幂等返回，不产生副作用。
   - 命中且当前用户不在 `orderers` 中：追加点菜人，按「名称 + 单位」补齐缺失的购物项，累加 `shoppingCount`，不新建记录。
   - 未命中：走第 6 步新建。
6. 新建时写 `OrderList`（`status = pending`，`orderers` 初始为一人）+ 逐条写 `ShoppingItem`（`sourceType = 'order'`，关联 `orderId`）；写入失败按补偿方式删除已写数据。
7. 返回成功。前端据结果区分提示：「已点菜」「已合并，共 N 人点」「你已点过这道菜」。
8. 分享为独立的用户动作，不进入点菜流程。

合并分支不做事务，因为订单已存在，追加点菜人与补建购物项失败时不会产生孤立数据；补建失败记录日志并返回 `shoppingFailed`，由前端提示手动补充。

### 6.2 取消点菜 `cancelOrder`

1. 条件更新 `OrderList`：`where({ _id, status: 'pending' })`，检查 `updated === 1`。
2. 同事务删除该 `orderId` 的全部 `ShoppingItem`，含已购买项。
3. 返回删除数量，供二次确认弹窗复核。
4. 已完成、已取消记录不允许再次变更。

### 6.3 加入家庭 `joinFamily`

单事务内一次性完成：

1. 当前 `openid` 无 `active` 的 `UserFamily`。
2. `Family.status = 'active'`。
3. `invite.code` 匹配且 `expiresAt` 未过期。
4. 有效成员数 < `maxMembers`。
5. 写 `UserFamily`（`role = 'member'`），更新 `Family.memberOpenids`。

错误尝试限流：按 `openid` 记录失败次数，超过阈值在一段时间内拒绝。限流数据存独立集合或云函数侧缓存，实施时选定。

### 6.4 购物清单合并

合并为前端纯函数 `groupShoppingItems(items)`，便于单元测试。规则：

1. 先按 `purchased` 分成「待购」「已购」两区。
2. 待购区内，`name` 相同且 `unit` 相同即可进入同一分组，再按 `quantity` 是否均为数值分成两类：
   - 都有数值：数量求和。
   - 都没有数值：合并为一行，`note` 去重后并列展示。
   - 一部分有数值、一部分没有：分为两行，不做相加。
3. 合并键：`name | unit | numeric`（`numeric` 取 `num` 或 `text`）。
4. 单位不同、已购与待购的项目互不合并。
5. 勾选合并组时，客户端提交组内全部 `itemIds`；服务端生成 `purchaseGroupId` 并批量置为已购。
6. 取消勾选时，按 `purchaseGroupId` 批量恢复。
7. 新增相同食材生成新的待购组，不并入已购组。

`purchaseGroupId` 是实施层新增字段，用于保证「整组购买 / 整组恢复」可追溯。它不改变需求定义的产品规则。

### 6.5 本地状态

| 状态 | 存储 | 规则 |
| --- | --- | --- |
| 已准备 | `prepared:{openid}:{dishId}:{version}` | 菜品 `version` 变化后旧键自动失效；提供一键清除 |
| 计时器 | `timer:{endAt,total,dishId,stepIndex}` | `setInterval` 只刷新显示；`onShow` 按 `endAt` 重算；仅一个进行中计时器 |

### 6.6 分享告知

**首版不做订阅消息**。`sendNotify` 整函数停用；订阅模板、字段 DATA ID、额度账本、`notifySummary`、D3 订阅开关与 S1 裁决项已关闭。

1. 记录页放置 `<button open-type="share">`，做成 56px 圆形图标按钮，居中固定在底部导航上方 16px。
2. 记录页定义 `onShareAppMessage`，同步返回固定 `title` 与 `path`。不定义该函数，转发入口不可用。
3. `path` 固定指向点菜记录页，**不带任何查询参数**。不传 `imageUrl`，使用微信默认页面截图。
4. 点菜成功后前端显示轻提示「已点菜，可分享给家人」。
5. 分享链路不调用云函数、不写数据库、不参与点菜事务。成员点开卡片后，云函数按 `openid + UserFamily` 取本人家庭数据；非本家庭成员无需特殊分支。
6. 未加入任何家庭的新用户由基线 `app.js` 全局绑定守卫导入创建／加入流程，属现有能力。
7. 验收按「能拉起转发、卡片内容与 `path` 正确、落地页数据归属正确」判定，并须真机验证。

按钮须清除 `button` 默认样式；列表底部留白避开按钮。规格见《design-spec.html》记录页标注。
